# 404 resolution — GSC export 2026-09-26

Source: `docs/seo/gsc-404-export.csv` (Search Console "Not found (404)", first
detected 3/24/26, re-checked live 26 Sep 2026). 62 URLs. Outcomes:

- **A** — already fixed (200 today), no action.
- **B** — has a live equivalent → 308, one hop.
- **C** — misspelling/variant of a real category → 308 to the correct slug.
- **D** — old `/categories/<24-hex-id>` from the pre-Next platform → mapped (308) or unmapped (410).
- **E** — internal/junk path, no live equivalent → 410.
- **F** — other host, can't be fixed from this repo.

All B/C/D(mapped) redirects and all 410s are generated from
[`lib/redirects.ts`](../../lib/redirects.ts) (`REDIRECT_RULES` /
`GONE_PATHS`), consumed by `next.config.ts` (`redirects()`) and `proxy.ts`
(410 responses). Verify with `scripts/check-redirect-map.sh`.

No current in-repo code links to any of the dead URLs below (checked by
grepping `app/` and `src/` for every distinct path) — the 404s are backlinks,
old app builds, WhatsApp templates, or crawl residue from the decommissioned
pre-Next platform, not links the current site still generates. Two exceptions
were found but don't produce these exact URLs: the footer's "Become Our
Partner" and "Freelancer Registration" links are dead `href="#"` placeholders,
not links to `/partner` or `/page/freelancer-registration` — flagged
separately below, out of scope for this redirect-map PR.

## Soft-404 fix

The triage doc separately flagged: any unknown `/category/<x>` returned HTTP
200 with `noindex` and "not found" copy instead of a real 404. Confirmed and
fixed. Cause: `app/category/[slug]/page.tsx` was a Client Component, and
`layout.tsx`'s `generateMetadata` called `notFound()` only after an awaited
fetch — metadata resolves concurrently with the page shell in this Next
version, so the shell's 200 was already committed by the time `notFound()`
ran. Fix: `page.tsx` is now a Server Component that checks the slug against
`lib/category-slugs.ts` and calls `notFound()` before anything renders (the
old client page moved to `category-page-client.tsx`, unchanged otherwise).
Unmapped slugs now return a real 404.

## Apex → www (pre-existing, outside this repo)

`restocare.in` (bare apex) already 308-redirects every path to
`www.restocare.in` — confirmed on the homepage and on already-working pages
(`/about`), so it's a platform-level canonicalization (Vercel domain config),
not something in `next.config.ts` or `proxy.ts`. It predates this PR and
applies site-wide, not just to the URLs below. For any bare-apex row in the
table, the real hop count in production is: apex → www (existing, outside
this repo) → the rule below (one hop, this repo). `scripts/check-redirect-map.sh`
tests the www host directly — where this repo's redirect map actually runs —
and separately notes the extra apex hop for visibility.

## Slug decisions (superseding an earlier internal triage doc)

Two slugs in an internal 2026-09-26 triage note conflicted with the original
brief. Per explicit confirmation, the original brief wins on both:

- Helpers & Waiter → `/category/helpers-and-waiters` (not `kitchen-helpers-waiters`)
- Technician → `/category/technician` (not `kitchen-equipment-repair`)

`/category/washing` and `/category/hire` (flagged in the triage doc as
"ask ops") have no confirmed live equivalent → 410, per the no-guessing
redirect rule. Update `lib/redirects.ts` if ops later identifies a real
target.

**Electrician** is live in the API as `isPublished: true` (confirmed via
`GET /v1/catagories`) and already ranks in GSC — this contradicts the
original brief's framing of Electrician as one of the "unpublished" categories.
Since publish state is backend-owned and out of scope here, this PR does
nothing to it: the existing `isPublished`-driven noindex/sitemap logic in
`app/category/[slug]/layout.tsx` and `app/sitemap.ts` already reflects
whatever the backend says. If Electrician should actually be noindexed to
match the "unpublished" framing, that's a backend data change, not a
frontend one — flagging for a decision, not resolving it here.
